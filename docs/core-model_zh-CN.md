# 核心模型

## App

每一个基于 Xira 的应用最终对应一个顶层结构体 `App` 为入口.  
它同时包含应用逻辑、框架运行时、数据存储.  

## ID系统

每一个struct和widget都应该有一个ID,  
如果这个部件不被其他组件依赖, ID 可以省略不写, 编译时自动分配.  

ID分为静态ID和动态ID.给某个部件的已知实例分配静态ID, 给未知的如运行时生成的分配动态ID.
静态ID在编译时嵌入,动态ID是 `部件名+运行时分配的数字ID`.
动态 ID 的数字部分在同类内唯一.  

## 数据模型

widget并不持有数据, 所有数据声明在 `App` 内, 通过 `component!` 宏声明.  

对于静态实例, 其数据在 App 中有固定位置,  
自动实现SoA, 全局同类型的在一个数组中存储, 用索引区分,  
App创建时先填充默认值(无默认值的需要开发者提供, 用于占位不关心具体值),
然后在该组件创建时运行其提供的初始化数据的函数覆盖原值.  

对于动态实例, 不与静态实例混存,  
但同类型的动态实例一起存储, 索引即其数字ID.  

## 依赖

依赖本质上是数据关系.  

依赖关系不由"谁创建谁"决定, 而是由"谁影响谁决定", 即使实践中2者常常重合.  

例如: 父组件销毁, 子组件随之销毁是因为子依赖父的布局, 父没了, 子无法独立布局.
这种"无法独立存在"的关系是存在性依赖.

依赖图必须是单向的 (无环). 有环意味着无法确定初始化顺序, 逻辑上无法创建.  

Xira 的数据处理顺序为:
数据变化 -> 值依赖传播 -> 存在性检查 -> 布局计算 -> 视图变化

Xira 代码分析器基于依赖理论构建:  
它从源码中提取依赖边, 为每条边附加条件谓词, 然后在编译期生成依赖图.
